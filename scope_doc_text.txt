RESEARCH DOCUMENT

Tiny Facade
An Offline Multilingual Tool-Calling Hub for On-Device AI
Expedition Tiny Aya | Cohere Labs

Authors: Bronson Bakunga, Kato Steven Mubiru
Affiliation: Crane AI Labs / Cohere Labs Community
Date: March 2026

Summary
Tiny Facade is an open-source Android service that runs a fine-tuned Tiny Aya model (3.35B parameters) locally on-device, providing multilingual tool calling and intent routing to any app that requests it. Instead of every app bundling its own copy of a language model (roughly 2GB each), Facade loads the model once and exposes a shared interface through Android’s AIDL system. Client apps send natural language instructions in English, Swahili, or Luganda, and Facade handles everything: understanding the input, generating the appropriate tool call, executing it, and returning the result. All offline.
This project investigates whether Tiny Aya-Earth can be fine-tuned (using Unsloth and synthetic data from Gemini 2.5 Flash) to reliably produce and execute structured function calls from multilingual prompts, and whether a shared service architecture meaningfully reduces storage, memory, and development overhead compared to per-app model bundling. We deliver the Facade inference service, two demo client apps (a multilingual offline assistant and a translation utility), a LoRA-adapted model with GGUF quantized variants, and benchmarks across tool-calling accuracy, latency, and resource usage on mid-range Android hardware.
SECTION 1
Problem & Why It Matters

Across sub-Saharan Africa and other emerging markets, mobile devices are the primary (and often only) computing platform. Developers building AI-powered apps for these users face a compounding problem: every app that wants to use a local language model must bundle its own copy of the model weights, its own inference runtime, and its own prompt engineering logic. For a 3B-parameter model quantized to 4-bit, that is roughly 2GB of storage per app. Three apps means 6GB of redundant model weights on a device that might only have 32GB of total storage. This is unsustainable.
Meanwhile, the users who would benefit most from offline, multilingual AI (farmers checking crop advisories in Luganda, health workers triaging symptoms in Swahili, merchants managing inventory in Hausa) are precisely those with the most constrained devices and the least reliable connectivity. They cannot afford cloud API calls, and they cannot afford the storage tax of every app shipping its own LLM.
The deeper technical gap is in tool calling. Cloud-based LLMs have mature function-calling capabilities, but on-device models, especially multilingual ones, lack reliable tool-calling support. Google's FunctionGemma (270M) targets English-only mobile actions. There is no equivalent for multilingual, low-resource language contexts. This means developers building local-language apps cannot easily connect a model to device APIs, local databases, or inter-app communication without extensive custom engineering.
Who Is Affected
Mobile developers in Africa and emerging markets building offline-first apps for local language speakers
End users on low-storage, low-connectivity Android devices who need AI tools in their native languages
The broader on-device AI research community, which lacks benchmarks and methods for multilingual tool calling at the edge
Cohere Labs and the Aya community, who need compelling on-device demonstrations of Tiny Aya's practical value
What Happens If This Goes Unsolved
Developers will either keep shipping bloated apps with redundant model copies (killing adoption on constrained devices), fall back to cloud-only solutions (excluding offline users), or simply not build for these languages at all. The promise of Tiny Aya as an on-device multilingual model remains a research artifact rather than a platform that unlocks an ecosystem.

SECTION 2
Research Question

Primary Question
Can a fine-tuned Tiny Aya model (3.35B parameters) perform reliable tool calling and intent routing on-device, serving as a shared inference service that multiple Android applications consume through structured intents, reducing per-app storage overhead while maintaining acceptable latency and multilingual accuracy across East African languages?

Sub-Questions
Tool-calling accuracy: How reliably can Tiny Aya-Earth generate structured function calls (JSON tool invocations) from natural language instructions in Luganda, Swahili, and English, compared to English-only baselines? (Top priority)
Shared inference viability: What is the storage saving, memory overhead, and latency profile of a shared Android service model vs. per-app bundled models on mid-range devices (4 to 6GB RAM)? (Second priority)
Intent routing: Can the model correctly classify and route intents from multiple client apps with distinct tool schemas? Each client app registers its own tool definitions, and the model matches the incoming instruction against the active schema, making this largely a prompt engineering problem rather than a classification challenge. (Last priority)
Prompt engineering vs. fine-tuning: What combination of system prompt templates, few-shot examples, and LoRA fine-tuning yields the best tool-calling F1 on a multilingual benchmark? (Third priority)

SECTION 3
Prior Work

On-Device LLM Inference
Google's AI Edge Function Calling SDK (2025) introduced on-device function calling for Android using the LLM Inference API with constrained decoding. It ships with formatters for Gemma and Hammer models but is English-centric and tightly coupled to the LiteRT/MediaPipe ecosystem. Google's FunctionGemma (270M) demonstrates fine-tuning a small model for mobile actions (calendar events, device controls) but covers only English and has no multilingual variant.
Apple's on-device Foundation Models (iOS 26, WWDC 2025) support tool calling via the Vercel AI SDK, enabling React Native apps to execute custom functions locally. This is iOS-only and English-first.
Off Grid and llama.cpp-based Android apps demonstrate that 1 to 3B models can run at usable speeds on modern phones, but tool calling support remains limited to models with built-in function-calling training.
Multilingual Small Language Models
Cohere Labs' Tiny Aya family (February 2026) represents the current state of the art for multilingual SLMs at the 3B scale. The base model covers 70+ languages. TinyAya-Earth is regionally optimized for African languages including Swahili. The models are available on HuggingFace, Kaggle, and Ollama, with an explicit design goal of on-device deployment.
InkubaLM (Lelapa AI, 2024) is a 0.4B model trained on 5 African languages but is too small for reliable tool calling. AfroLM (Dossou et al., EMNLP 2022) covers 23 African languages for classification tasks but is an encoder-only model unsuitable for generation.
Shared Model Services on Mobile
Android's AICore system service (Android 14+) provides a shared Gemini Nano model that multiple apps access through ML Kit GenAI APIs. This is the closest architectural precedent to what we propose, but it is limited to Gemini Nano, closed-source, and unavailable on most devices in our target markets. The NNAPI provides lower-level shared inference but requires per-app model loading.
No prior work combines multilingual tool calling, shared on-device inference, and an open-source model targeting low-resource African languages.
Key Gap
There is no open-source, on-device, multilingual tool-calling framework that allows multiple apps to share a single model instance, particularly not one optimized for African languages. This project sits at the intersection of three active research areas (on-device LLMs, multilingual AI, function calling) that have not yet been connected.

SECTION 5
Simplest Experimental Setting

The minimum viable experiment to test the core hypothesis has three layers:
Layer 1: Can Tiny Aya Do Tool Calling At All?
Take TinyAya-Earth (or TinyAya-Global) and test its zero-shot ability to generate structured JSON function calls from natural language prompts in English, Swahili, and Luganda. Use a set of 5 to 10 simple tool definitions (get_weather, set_alarm, translate_text, search_contacts, send_message) and measure whether the model outputs valid, parseable tool calls. This requires only Ollama on a free Colab/Kaggle notebook, no Android development needed.
Layer 2: Can Prompt Engineering or LoRA Fix It?
If zero-shot performance is poor (likely), apply progressive interventions: system prompt with tool schema and few-shot examples, constrained decoding to force JSON output, and finally a LoRA fine-tune using Unsloth on a synthetic tool-calling dataset in English, Swahili, and Luganda. Measure F1 at each stage. This requires a single GPU (T4 on Colab or A100 on RunPod for faster iteration).
Layer 3: Does the Shared Service Architecture Work?
Build the minimal Android service: one app running inference via llama.cpp or MLC-LLM, exposing an AIDL or ContentProvider interface. Facade receives natural language input, generates the tool call, executes it, and returns the result. Build one trivial client app that acts as a thin UI layer, sending requests and displaying results. Measure cold start time, inference latency, memory footprint, and compare against the same client app with the model bundled internally.

Evaluation Approach
We construct a multilingual tool-calling evaluation set of roughly 200 examples per language (English, Swahili, Luganda), each consisting of a natural language instruction, a set of available tool definitions, and the expected structured output. Examples are generated synthetically using Gemini 2.5 Flash and validated by native speakers. This keeps the dataset small enough to iterate quickly while covering the core capability.

SECTION 9
Scope, Non-Goals & Priorities

Non-Goals
These are strategic decisions to maintain focus, not failures:
We are not building a general-purpose on-device assistant. The model handles tool calling and intent routing, not open-ended conversation.
We are not targeting iOS. Android-first, because it dominates the target markets (>85% market share in sub-Saharan Africa).
We are not trying to achieve parity with cloud-based function calling (Gemini 2.5 Flash, Claude). We want "good enough" tool-calling accuracy for a defined set of tool schemas.
We are not building production-grade security or sandboxing for the shared service in v1. Trust model is basic.
We are not covering all 70+ Tiny Aya languages. We focus on English, Swahili, and Luganda, the languages where we have native speaker access for validation.
Scope for v1
The Facade Inference Service
An Android app/service that loads TinyAya-Earth (GGUF quantized) and exposes an AIDL interface for other apps to send natural language instructions in any supported language. Facade understands the input, generates the appropriate structured tool call, executes it, and returns the result to the client. Includes a simple built-in chat UI for direct testing and custom instruction entry.

Demo App 1: Multilingual Offline Assistant
A lightweight assistant where users can issue natural language commands like “piga simu kwa mama” (call mom in Swahili) or “tumira obubaka eri John” (send a message to John in Luganda). The app sends the instruction to Facade, which understands it, generates the tool call, executes the action (e.g., initiating a phone call or sending a message), and returns the result. The client app is just a thin UI layer. Demonstrates real-world utility for users who think and speak in their native language.

Demo App 2: Local Translation & Dictionary
A translation utility where users input text and Facade handles the full pipeline: detecting the source language, performing the translation between English, Swahili, and Luganda, and returning the result. The client app simply collects input and displays output. Demonstrates a different tool schema routed through the same shared service, showing that Facade handles heterogeneous tasks from different client apps.


Priorities
P1 (Must Have): Reliable multilingual tool-calling from Tiny Aya with measurable accuracy. This is the research contribution.
P2 (Must Have): Working Android shared inference service with at least one demo client app.
P3 (Should Have): Second demo app proving the shared model pattern. Storage and latency benchmarks.
P4 (Nice to Have): Agent Skills SDK, a developer-facing library/template for building new client apps. Geospatial-aware tool calling. Voice input pipeline.
Known Limitations
3.35B models are inherently less capable than 7B+ models for complex reasoning and multi-step tool chains. We accept single-turn tool calling as the scope.
Luganda has very limited digital text corpora; tool-calling accuracy in Luganda will likely lag behind Swahili and English.
On mid-range phones (4GB RAM), inference speed may be below 2 tokens/second for the full 3.35B model. We may need aggressive quantization (Q4_K_M or lower).
The CC-BY-NC license on Tiny Aya restricts commercial deployment. This is a research project; commercial licensing would need separate arrangement with Cohere.
No human evaluation of output quality in v1. We rely on automated metrics (F1, schema compliance) for speed of iteration.
